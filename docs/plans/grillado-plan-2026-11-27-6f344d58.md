# Plan to build loop: build steps, progress, asks and change notices

## Problem

When a coding agent builds from a Grillado plan, Grillado goes quiet once the plan is handed over. The plan has no proper list of steps for the agent to follow. The agent has no way to say which step it is on, what it verified or where it moved away from the plan, so all of that ends up only in chat. After the build, the plan still looks untouched.

When the agent hits a decision the plan does not cover, the build skill tells it to "send open decisions back to the user". The only ways to do that today are a comment on the plan or a question in chat. Neither one comes back as a decision in the plan.

If the user answers another round or edits the plan during the build, nothing tells the agent. It finds out by accident, or not at all.

A plan started from the shell runs on whichever agent the web app has selected. The coding agent cannot choose, and one of the available agents cannot read the project.

## Solution

Every plated plan gets a first-class **Build steps** section: thin end-to-end slices, each with a check that tells you it is done. The user can edit, reorder, add and remove these steps in the plan view.

A new `grillado build` command lets the coding agent:
- get the next step
- report a step as started or done (with what it verified and any deviations)
- ask the user a decision, wait for the answer, and withdraw an ask it no longer needs

Each of these has a matching MCP tool.

An ask appears as an ember card pinned above the plan, marked "Agent is waiting". It shows the agent's options and can be answered with number keys and Enter. The answer becomes a cited decision in the plan and is sent back to the agent. When the plan is not on screen, the tab title and the plans list show that an agent is waiting.

Every build command reply includes the plan's revision. If the plan changed since the agent last read it, the reply says what changed.

The markdown file on disk records progress: a status checkbox on each step, plus a Build log section.

`grillado plan start` gets an optional `--agent` flag. It refuses agents that cannot read the project.

All of this ships together as one slice.

## User stories

1. As a user, I want every plated plan to include a Build steps section of thin end-to-end slices, so that my coding agent has a clear order of work.
2. As a user, I want each build step to carry a done check, so that "done" means something I can verify.
3. As a user, I want Send to issues to reuse the plan's Build steps, so that issues and build steps never disagree.
4. As a user, I want to edit a step's title and done check in the plan view, so that I can fix steps that are off.
5. As a keyboard user, I want to reorder steps with the keyboard, so that I can change the build order without a mouse.
6. As a user, I want to add and remove build steps, so that the plan matches what I actually want built.
7. As a coding agent, I want `grillado build next <plan>` to give me the next step that is not done, with its done check, so that I always work on the right thing.
8. As a coding agent, I want to report a step as started, so that the user can see what I am working on.
9. As a coding agent, I want to mark a step done with what I verified and any deviations, so that the build record lives in the plan and not only in chat.
10. As a user, I want a step the agent marked done to show Done at once, and I want to be able to reopen it, so that I stay in control without being a bottleneck.
11. As a coding agent, I want to ask the user a decision with my own options, so that I never have to guess.
12. As a coding agent, I want `grillado build wait` to block until the ask is answered, timing out and re-run like `plan wait`, so that long waits work the same way as plan waits.
13. As a coding agent, I want to withdraw an ask I no longer need, so that the user is not left with stale questions.
14. As a user, I want an ask shown as a pinned ember card marked "Agent is waiting", answerable with number keys and Enter, so that I can unblock the agent quickly.
15. As a user, I want a withdrawn ask to show as withdrawn and never as decided, so that the plan only holds decisions I made.
16. As a user, I want my answer added to Implementation decisions with a build citation and the step it was decided at, so that I can trace it later.
17. As a user who is not looking at the plan, I want the tab title to show a waiting count and the plan to show an ember badge in the plans list, so that I notice a blocked agent.
18. As a coding agent, I want every build command reply to include the plan revision and what changed since my last read, so that I notice new decisions and edited sections or steps.
19. As a user, I want the plan's markdown file to show each step's status and a Build log of what was verified, what deviated, and how each ask ended, so that the file on disk tells the full story of the build.
20. As a coding agent, I want to pass `--agent <id>` to `plan start`, so that I can choose which agent writes the plan.
21. As a coding agent, I want a clear error that lists the agents that can read the project when the one I chose cannot, so that I can fix my command right away.
22. As an MCP user, I want build tools that match the shell commands one-to-one, so that both ways of driving Grillado can do the same things.
23. As a user, I want the step list, ask card and badges to work by keyboard, at 390 px, in dark and light themes, and without accessibility violations, so that the build loop meets the same bar as the rest of Grillado.

## Implementation decisions

- **One slice.** Build steps, progress reporting, asks and change notices ship together, in both the shell commands and the MCP server. No subset ships first. [R1:first-ship-scope]
- **Build steps are written at plating.**
  - The plan run writes a Build steps section in which every step has a title and a done check. This changes the plan prompts and plan contracts in `src/core/prompts.ts` (`SYNTHESIS_METHOD`, `PLAN_CONTRACT`, `READ_PLAN_CONTRACT`) and the plan validation in `src/core/schema.ts`. It keeps the existing validation and its single repair retry. [R1:build-steps-source]
  - Each step gets a stable key, so that progress, asks and citations can refer to it. [R1:build-steps-source]
- **Send to issues reuses the steps.** In `src/core/issues.ts`, the plan's Build steps become the first source of Slices (key, title, body, covers, sections), ahead of the existing Tasks-checklist and User-stories fallbacks and the agent split run. For a plan with Build steps, Send to issues does not split the plan again. [R1:build-steps-source]
- **Step editing.**
  - The plan view lets the user edit a step's title and done check, reorder steps with the keyboard, and add or remove steps. [R2:step-editing]
  - Every edit moves the plan revision, so it shows up in the agent's next reply. [R2:step-editing]
  - This builds on the existing plan editor (`web/src/app/editor/PlanEditor.tsx`, `web/src/app/editor/blocks.ts`), shown through `web/src/app/Plan.tsx`. [R2:step-editing]
- **What "done" means and who marks it.**
  - The agent marks a step done itself and must include what it verified and any deviations. [R1:step-done-rule]
  - The step shows Done at once. The user can reopen it, which also moves the revision. [R1:step-done-rule]
  - Step status is a progress report, not a change to the plan's content. [R1:step-done-rule]
- **Command shape.**
  - Add a new verb, `grillado build next|start|done|ask|wait|withdraw <plan>`, next to `src/cli/plan-command.ts`, wired through `src/cli/main.ts` and `src/cli/args.ts`. [R2:build-command-shape]
  - Each command has a matching `build_*` tool registered in `src/cli/mcp.ts`, next to the seven existing tools. [R2:build-command-shape]
  - The shared build-state logic lives in one place both of them call, alongside `src/cli/plans.ts`. [R2:build-command-shape]
- **Asks.**
  - An ask carries a key, a question, the agent's options and the step it was raised at. [R1:ask-card-look]
  - In the browser, an ask appears as a card pinned above the plan, with an ember "Agent is waiting" tag, the options, number-key selection and Enter to send. It should reuse the existing question card (`web/src/components/ui/uai/agent-question.tsx`, `web/src/app/Round.tsx`). [R1:ask-card-look]
- **Unanswered asks.**
  - `build wait` behaves like `plan wait`: it returns a "waiting" result after `DEFAULT_WAIT_S` (540 s) and is re-run. [R1:unanswered-ask]
  - The agent may withdraw an ask it no longer needs. A withdrawn ask shows as withdrawn and is never recorded as a decision. [R1:unanswered-ask]
  - Nothing ever answers an ask on the user's behalf. [R1:unanswered-ask]
- **Answer citation.** An answered ask becomes a bullet under Implementation decisions, tagged `[B:<ask-key>]` and marked as decided during the build at step N. The answer is also returned to the waiting agent. Decision metadata parsing (`src/core/decision-block.ts`, `web/src/app/editor/decision-meta.ts`) must accept the `B:` form next to `R<n>:`. [R2:ask-answer-citation]
- **Plan change signal.**
  - Every build command reply includes the plan's current revision. [R1:plan-change-signal]
  - When the revision has moved since the agent's last `get`, the reply says so and lists what changed: new decisions, edited sections and step edits. [R1:plan-change-signal]
- **Progress on disk.**
  - In the plan's markdown file (in the project's plans folder, `docs/plans` by default), each Build step line carries a status mark: `[ ]`, started, or `[x]`. [R2:progress-on-disk]
  - A Build log section lists, per step, what was verified and any deviations. It also lists each ask and whether it was answered or withdrawn. [R2:progress-on-disk]
- **Notice while away.**
  - When an ask is open and the plan is not on screen, the tab title shows a waiting count, for example "(1) Agent is waiting". [R2:ask-notify]
  - The plan gets an ember badge in the plans list (`web/src/app/Tree.tsx`, `web/src/app/counts.ts`). [R2:ask-notify]
  - There are no OS notifications. [R2:ask-notify]
- **Choosing the agent from the shell.**
  - `plan start` (and the MCP equivalent) accepts an optional `--agent <id>`. Without it, Grillado uses the configured `defaultProvider`, or else the first entry of `PROVIDER_IDS`, as in `src/cli/plans.ts` today. [R2:agent-choice-from-shell]
  - If the chosen agent cannot read the project, as reported by its provider in `src/core/providers/types.ts`, the start is refused with a clear error that lists the agents that can. [R2:agent-choice-from-shell]
- **Skills.** The build skill (`skills/grillado/SKILL.md` and `src/cli/skills-command.ts`) must tell agents to:
  - use `grillado build` to ask decisions instead of commenting or asking in chat
  - re-read the plan when a reply reports a change
  - report done with what was verified and any deviations

  This follows from [R1:first-ship-scope] and [R2:build-command-shape].

## Testing decisions

- **Core behavior (unit tests, in the style of `test/issues.test.ts` and `test/rounds.test.ts`):**
  - Plan replies with Build steps pass validation, and replies with malformed steps are repaired or rejected.
  - Send to issues uses the Build steps when they exist and falls back as it does today when they don't.
  - Rendering the markdown produces the step checkboxes and Build log entries for every combination of statuses and ask outcomes.
  - `[B:key]` citations parse next to round citations.
- **Shell commands (in the style of `test/agent-commands.test.ts`, with `test/fixtures/fake-agent.mjs`):**
  - Drive `grillado build next|start|done|ask|wait|withdraw` from outside.
  - `next` skips done steps and respects the user's order.
  - `done` without a verification note is refused.
  - `wait` returns "waiting" on timeout and the answer once one is given.
  - `withdraw` leaves no decision behind.
  - Every reply carries the revision and reports changes after a new round, a section edit, a step edit or a reopened step.
- **MCP parity (`test/mcp.test.ts`, `test/mcp-fixture.ts`):** every `build_*` tool returns the same results as its shell command for the same steps.
- **Agent choice:** `plan start --agent` uses the chosen agent, falls back to the default when the flag is absent, and refuses an agent that cannot read the project with an error that lists the ones that can.
- **Server (`test/server.test.ts`):**
  - Answering an ask writes the cited decision to the plan, moves the revision and releases the waiting agent.
  - Reopening a step moves the revision.
- **Browser (e2e in `e2e/`, in the style of `e2e/mcp.mjs` and `e2e/editor.mjs`):**
  - The ask card appears pinned above the plan with the "Agent is waiting" tag and can be answered with number keys and Enter.
  - The tab title count and the plans-list badge appear and clear.
  - Steps can be edited, reordered by keyboard, added and removed.
  - All of this works at 390 px, in dark and light themes, with no accessibility violations.
  - Some e2e checks already fail on this machine before any change, so judge results against that known baseline.
- **What makes a good test:** it checks what the user or the agent can see (command output, MCP results, the markdown file, the page), not internal state shapes.

## Out of scope

- Grillado writing product code or running build commands. It only hands the plan over and listens back.
- Any agent, or Grillado itself, answering an ask or confirming a plan for the user.
- OS or desktop notifications. The notice stays inside the browser.
- A partial first release. The loop ships whole.

## Assumptions and open decisions

- **Assumption:** the plan revision is a single counter (or hash) per plan, and anything that changes content or step status moves it: a round, a section edit, a step edit or reorder, a reopened step, an answered ask.
- **Assumption:** a plan plated before this slice has no Build steps. `build next` on such a plan returns a clear message instead of making steps up.
- **Assumption:** reopening a done step sets it back to not started and keeps its earlier Build log entry as history.
- **Assumption:** several asks can be open at once. The tab title count is the number of open asks across all plans.
- No open decisions were left from the interview.

### Plan change notice: On every reply

```sh
$ grillado plan step done 2026-11-26-b7e1 3 --note "status saved in session.json"
Step 3 done.
The plan changed since you last read it (rev 7 -> 9):
  + decision [R3:ask-storage] Sidecar build.json
  ~ Implementation decisions edited
Run `grillado plan get 2026-11-26-b7e1` before the next step.

$ grillado plan next 2026-11-26-b7e1
Step 4: Plan view shows status and asks
Done when: ...
```

### Progress in plan file: Inline + Build log

```markdown
## Build steps

- [x] 1. Store build steps on the plan
  Done when: `plan get` returns steps with status
- [~] 2. Ask a decision from the shell (started)
- [ ] 3. Ask card in the plan view

## Build log

- Step 1 done — verified: unit tests in plans.test.ts pass.
  Deviation: kept the step list in the session, not in a separate file.
- Ask `ask-timeout` answered: "Agent may withdraw" [B:ask-timeout]
```

### Command names: New `build` verb

```sh
grillado build next  plan-b7e14b3d
grillado build start plan-b7e14b3d --step 2
grillado build done  plan-b7e14b3d --step 2 \
  --verified "plans.test.ts pass" --deviation "kept steps in session"

grillado build ask plan-b7e14b3d --key ask-timeout \
  --title "Withdraw asks after a timeout?" \
  --option a="Keep waiting" --option b="Withdraw after 1 h"
grillado build wait plan-b7e14b3d --ask ask-timeout   # up to 540 s, re-run
grillado build withdraw plan-b7e14b3d --ask ask-timeout
```
